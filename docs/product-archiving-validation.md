# Удалённые товары — реализация и локальная проверка

Дата: 24 сентября 2026

Старая админка `merch-store` опубликована 24 сентября 2026 с разрешения пользователя. Ручное удаление работает и при положительном остатке. Новая `merch-platform` не изменялась и не публиковалась.

## Поведение

- Автоматическая отметка после 30 полных суток непрерывного нуля, при возрасте карточки не менее 30 суток
- Для существующих товаров нулевой интервал восстанавливается по датам продаж и поступлений, включая продажи, исключённые из статистики. Отрицательные промежуточные остатки, некорректные количества и отсутствующие даты выводятся как исключения; такие карточки автоматически не скрываются
- Кнопка «Удалить» ставит мягкую отметку при любом корректном неотрицательном остатке. Количество в карточке сохраняется. Повтор не продлевает срок хранения
- В каталоге и выборе товара для поступления есть «Показать удалённые». История продаж и поступлений видна независимо от этой галочки
- Приход или возврат, увеличивающий количество, восстанавливает существующую карточку в той же транзакции, что и остаток. Уменьшение сохранённого количества при исправлении истории само по себе не восстанавливает карточку
- «Восстановить» при нуле сохраняет известную дату нулевого остатка и даёт 30 суток отсрочки по отдельному серверному `restoredAt`
- Через два календарных года после фактического `deletedAt` карточка очищается при очередном запуске. Для 29 февраля используется 28 февраля через два года с сохранением времени
- Подготовка исторических данных начинается за 30 суток до очистки. В строках операций остаются минимальные данные для прежних расчётов: название, категория, размер, бренд, состояние, цены и идентификатор. Это не отдельный архив полных карточек
- После физического удаления сохраняются отчёты и строки операций. Изменения количества отсутствующего товара блокируются; редактирование не относящихся к остатку полей сохраняет исторический снимок

## История и дашборд

Прибыль, планы, ABC, маржинальность, анализ размеров, средний срок продажи и процент проданных вещей используют текущую карточку, а после окончательной очистки — сохранённые данные строк. Таким образом сохраняется прежняя модель расчёта: историческая себестоимость не выдумывается, для старых операций фиксируется прежняя оценка по карточке (`source: catalog_estimate`). Выручка, чеки и топ продаж продолжают использовать исходные операции.

Количество позиций, текущий складской остаток, распределение вещей, залежавшиеся вещи и коэффициент наценки относятся к активному каталогу. Сохранённое количество удалённой карточки в эти показатели не входит. В размерном анализе и оборачиваемости сохраняются прошлые продажи, а текущий остаток считается по активным карточкам. После восстановления сохранённое количество снова учитывается.

## Бесплатное обслуживание и согласованность

Платных служб нет: Spark, без Functions, Scheduler, TTL и биллинга. Обслуживание запускается после загрузки админки или обновления дашборда. Отдельного постоянного таймера нет.

`_maintenance/productLifecycle` хранит `enabled`, `revision`, `lastStartedAt`, `runId`, `steps`. По умолчанию автоматическая обработка выключена. Для тестовой базы она явно включена.

- На всю базу разрешён один запуск за 24 часа и до 60 шагов. Шаг — одна изменяемая карточка либо один документ истории и обновление служебного состояния. Окончательное удаление — отдельный шаг
- Успешный запуск требует не более 121 записи документов, включая резервирование запуска; удаления входят в те же 60 шагов. Это ограничение обслуживания, не всей админки
- На шаг приходится до трёх явных чтений в транзакции; дополнительно расходуются чтения состояния, обновление затронутых строк интерфейса и обращения Security Rules. Начальная загрузка приложения, другие вкладки и обычные операции имеют собственный расход
- Для обслуживания транзакции выполняются без повторных попыток. Конфликт, ошибка доступа или сети останавливает цикл. Повторная подготовка истории пропускает уже сохранённые снимки той же версии
- Обычные операции сохраняют стандартную транзакционную защиту и ограниченно повторяются при подтверждённом конфликте общей ревизии. Идентификатор операции не меняется, двойного поступления не возникает
- Все пути записи старой админки увеличивают ревизию. Перед обработкой используется серверная ревизия и полный загруженный с сервера набор товаров и истории; отсутствие `date` не исключает документ из проверки
- Смена учётной записи прекращает цикл и отбрасывает запоздавшие ответы загрузки

Если никто не открывает админку или достигнут предел обработки, очистка откладывается. Это не гарантия удаления ровно в секунду двухлетия. Один снимок Firebase Usage не доказывает соблюдение всех общих квот в будущем; суточные пики, хранение и трафик перед включением необходимо проверить отдельно. Изменения не подключают платный тариф.

## Локальный запуск

Требуются Node.js, Docker Desktop, Chrome и зависимости `npm ci`. `npm test` скачивает проверенный по SHA-256 Firestore Emulator, если его ещё нет.

```powershell
npm test
npm run start:demo
```

Адрес: http://127.0.0.1:8080

Запускается именно интерфейс старой админки, с вымышленными товарами и автоматическим тестовым входом владельца. Плашка сверху обозначает тестовый режим. База `demo-merch-archive` работает только на loopback-порту 18081. Изменения тестовых товаров не записываются в магазин. При новом запуске демонстрационная база создаётся заново.

Обычная команда `npm start` сохраняет штатную конфигурацию Firebase; для изолированной проверки этой доработки используется именно `start:demo`.

## Проверки

Итоговый локальный `npm test` после разрешения удаления положительных остатков завершился успешно: 8 модульных тестов, 4 сочетания экрана/темы с 9 комбинациями фильтров, 4 браузерных набора проверки состояния товара, 31 складской сценарий и 17 групп проверок жизненного цикла. Проверены сохранение количества, исключение из текущего склада, неизменность прибыли, отсутствие самовольного восстановления фоновым обслуживанием, прибавление прихода к сохранённому остатку и двухлетняя очистка. Кнопки удаления/восстановления положительного остатка проверены в Chrome при 1440, 390 и 320 px в обеих темах.

- Модульные сценарии: граница 30 суток, возраст карточки, восстановление, доверенная история, противоречивые данные, високосный год, видимость положительных остатков
- Прежние браузерные проверки фильтров, классификации новых/б/у товаров, форм и расчётов
- Прежняя проверка складских транзакций: повторный запрос, конкурирующие вкладки, устаревшие формы и отклонение записи правилами
- Новые браузерные проверки: первичная обработка старого нуля, ручная отметка, восстановление приходом, сохранность истории и дашборда после очистки, серверный запрет раннего физического удаления, дневное ограничение, два параллельных клиента, продолжение большой истории на следующий день, неизвестные даты, смена аккаунта
- Визуальные проверки Chrome: 1440, 390 и 320 px, светлая и тёмная темы. Снимки и машинный отчёт находятся в игнорируемом `output/archive`

Браузерные тесты разрешают доступ только к локальной странице, эмулятору и загрузке Firebase SDK с gstatic. Обращений к production Firestore нет.
